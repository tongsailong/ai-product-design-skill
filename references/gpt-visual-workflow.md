# GPT-first 视觉工作流 · 让 GPT 负责视觉创意，DesignWise 负责工程实现

> **读这份文档的时机**：App / Web / 交互原型类任务，需要先探索视觉方向、或需要为正式设计配图时。
>
> **一句话立场**：本文件**不替换**原有 HTML/CSS 三方向探索，而是在它之上加一条**更靠前的 GPT 视觉探索通路**——让 GPT 出概念效果图与正式图片素材，DesignWise 出可运行的真实 UI，用户保留方向选择权。**GPT 不可用时，原有 HTML/CSS 通路原样保留，能力一条不减。**
>
> **与 `references/product-value.md` 同构**：都是「在原有流程上加一层判断」，不新增检查点，不新增并行流程。

---

## 0. 全流程（九个环节）

```
需求理解 → Visual Brief（产品需求/画像/价值/设计目标 → 三方向共同输入 + 参考资产）
  → ⓪ GPT Concept 判断：能力探测 + 🔴 付费资源授权 Gate（未授权 → 不调生图，回落 HTML/CSS）
  → ① GPT 生成三套差异化视觉效果图（概念参考）
  → ② 用户选择 / 组合 / 局部修改 / 重新生成
  → ③ 锁定设计方向（写 direction-approved.md，Gate）
  → ③.5 概念图 → 视觉规范转译（吸收/否决/落实现记录，§3.5）
  → ④ GPT 生成正式产品图片素材（插画 / 背景 / 场景图）
  → ⑤ DesignWise 实现真实 HTML/CSS/React UI
  → ⑥ 视觉还原检查 + 功能与交互验收
  → ⑦ 设计交付包（Web/Android/PPT 交付契约，`design-handoff.md`）
```

> **三个"是否"的默认答案**（防止过度生成）：**没有新设计任务**／**结构性任务（幻灯片/信息图/动画）** → 不进本通路；**有设计任务但 GPT 未授权或不可用** → 回落 HTML/CSS；**已获充分设计依据** → 停止探索、推进实现（不自造生图步骤）。

**职责分工（不变式）**：

| 谁 | 负责 | 不负责 |
|---|---|---|
| **GPT（图像生成）** | 视觉创意探索、概念效果图、原创插画/背景/场景图 | 产品判断、真实 UI、交互逻辑 |
| **DesignWise** | 需求理解、产品价值判断、工程实现、验收 | 不做视觉创意赌博，不把效果图当界面交付 |
| **用户** | 最终设计方向选择权（唯一能做的决策） | —— |

**判断顺序仍是**：有用 → 好懂 → 舒服 → 有意义。GPT 出的图再好看，不解决真实用户问题就是精致的 slop。

## 1. 能力探测（第一步，必须实测，不得凭配置断言）

GPT 指 **OpenAI 实际提供的图像生成能力**（gpt-image 系列），不得用其他模型冒充。

🔴 **模型口径（唯一权威，勿在别处重复写死版本号）**：默认模型**不在此文件硬编码**，而由能力检测确定的**当前可用型号**决定。判定顺序：① `gen_via_cpa.py --health` 返回的 `允许的图片模型` 清单（实测 2026-10-13 含 `gpt-image-2.5` / `gpt-image-2` / `gpt-image-1.5` 等）；② 脚本的 `DEFAULT_IMAGE_MODEL`（可由环境变量 `CPA_IMAGE_MODEL` 覆盖）。**取两者交集里最可用的 gpt-image 系列型号**；当前实测默认即 `gpt-image-2.5`。
> 调用时**不必显式传 `--model`**（走脚本默认值即最新已验证型号）；只有当检测出的默认型号变化、或需改用清单内其它型号时，才须按 §1.5 重新取得授权，且型号名仍须落在 gpt-image 系列内。
> ⚠️ **别把 `gpt-image-2.5` 抄进多个文档**——SKILL.md 等位置一律**引用本节**（写「§1 默认模型」而非字面版本号），型号升级时只改本处口径，不产生多处失同步。

**铁律：发现模型名 / 工具配置 / API 文档 ≠ 生图可用。** 只有真实调用并拿回图片才算通过。

**探测三步（按序，任一步给不出结论就往下走）**：

> 🔴 **授权前置——第 1、2 步零成本，第 3 步会真实出图**：第 1 步 `--health` 只探测接口、不出图、不花额度，可直接跑；**第 3 步「真实出图」会消耗额度或产生费用**——执行前先向用户说明「调用哪个模型、出几张、走哪条链路、是否计费」，**取得明确授权后再跑**（口径与 §7「付费调用前置」一致）。**未获授权时不得擅自出图**：按 FAIL 回退 HTML/CSS 三方向，或停下询问用户——**不得以「探测需要」为由绕过授权**。

1. **有没有生图通路**：查当前环境是否存在可调用的图像生成能力
   - 本机首选：`huashu-gpt-image` 技能自带的 `gen_via_cpa.py --health`（只探测、不出图、不花额度）
   - 其他环境：OpenAI Images API（`/v1/images/generations`、`/v1/images/edits`）或等价服务
2. **是不是真 GPT**：确认返回的模型名属 **gpt-image 系列**（如 `gpt-image-2.5` / `gpt-image-2` / `gpt-image-1.5`）。模型名对不上 → 不叫 GPT 生图，如实说明。
3. **真实出图（🔴 付费步骤，须先过上方授权前置）**：用一张最小测试图实跑一次，确认：

| 检查项 | 判定 |
|---|---|
| 是否真实调用生图端点 | 有本次调用的成功记录（响应 / usage 记录），可关联到输出文件 |
| 是否返回实际图片 | 文件存在、能解码打开、非空白/纯色 |
| 能否本地保存 | 落盘成功，不依赖临时链接 |
| 尺寸、格式正确 | 目标像素 / PNG 或 JPG，元数据与预期一致 |
| 是否支持后续编辑 | 图生图（参考图编辑）通路存在 |
| 是否满足素材使用需求 | 单元素、可集成、无多余 UI |

> ⚠️ **来源证据不可省**：普通程序（SVG + 图像合成）也能产出「像样的 PNG」。判「真模型生成」须有**本次调用成功记录 + 与输出文件的关联**；只检查「目录里多了文件」「PNG 里没有元数据」都不够。

**探测结论只有两种**：
- **PASS**：真实 GPT 生图成功 → 走本文件第 2-6 节。
- **FAIL**：不可用 → **不改工作流**，保留原有 HTML/CSS 三方向通路，向用户报告最简单的接入方案与阻塞条件。**不得假装成功，不得用 HTML 截图冒充 GPT 生成图。**

> ⚠️ **PASS ≠ 有权出图**：探测通过只说明「通路存在」。是否**允许调用**由 §1.5 授权 Gate 决定。

## 1.5 付费资源授权 Gate（🔴 硬门 · 物化可查）

> **一句话**：**没有用户本轮的明确授权，一次生图都不许发。** 能力探测通过 ≠ 有权调用——「工具没拦 ≠ 有权执行」（与用户全局规范 §2 一致）。

**Gate 四要素**（四者齐备才算过门，缺一即拦）：

| # | 要素 | 口径 |
|---|---|---|
| 1 | **用户本轮原话** | 必须来自用户**本人本轮**发出的消息；agent 自行推断、旁证、沉默、「上次同意过」**一律无效** |
| 2 | **模型** | 默认 `gpt-image-2.5`（§1）；改用其它型号须重新确认 |
| 3 | **张数 / 额度上限** | 概念阶段默认「每方向 1 张 × 3 方向」；正式素材按需列清单。**超出上限须再次授权** |
| 4 | **是否计费** | 说明走哪条链路、是否按量计费、预计费用 |

**物化落地**（呼应 SKILL.md「Gate文件协议」）：过门后把上述四要素写入项目 `direction-approved.md` 的 `## GPT 出图授权` 一节。**该节不存在 = 未授权 = 禁止调用生图**——任何模型都能自查，hook 也能 grep 硬拦。

**拦截后的合法动作**：
- **未授权** → 不得调用生图；按 FAIL 处理，**原样走 HTML/CSS 三方向**，或停下问用户「是否授权用 `gpt-image-2.5` 出 N 张概念图」
- **零成本例外** → §1 第 1 步 `--health` 只探测、不出图、不计费，可直接跑（结论仍须并入判断）
- **禁止** → 以「探测需要」「流程要求」为由绕过授权；用 HTML 截图冒充 GPT 生成图

## 2. 概念效果图：三方向 GPT 探索

### 2.0 Visual Brief（三方向探索的共同输入 · 自动生成）

**为什么**：prompt 的质量上限由输入决定。三张概念图若共用一句含糊需求，必然糊成同一张；差异来自**同一份 Brief 的三个不同侧写**。所以先由 agent **自动生成**一份 `design-brief.md`（`huashu-gpt-image/references/prompt-patterns.md` 的方法论照用，本 skill 只规定输入结构）。

**Brief 六段（从产品需求自动推导，用户无需参与）**：

| 段 | 内容 | 来源 |
|---|---|---|
| 1. 产品定位 | 是什么、一句话说清、不可变的结构边界（tab/页面数） | spec.md |
| 2. 用户画像 | 一个具体人物 + 一个具体时刻 + 由画像推出的硬 UX 约束（字号/点击区/无障碍） | spec.md |
| 3. 核心价值 | 有用→好懂→舒服→有意义 四层，各一行 | `references/product-value.md` |
| 4. 情绪目标 | **要什么**（一处真实情绪机会，见下；没有就写「本版不加情绪价值」）/ **不要什么**（硬门控：禁焦虑、禁伪成就、禁医疗暗示） | spec.md + `references/product-value.md` §0.5 |
| 5. 视觉关键词 + 色彩 | 整体 + 逐页关键词；已知 token 色值（有则填） | 品牌资产 / 已定方向 |
| 6. 差异化维度表 | 三个方向各自的**母题 / 骨架 / 情绪**（见下） | §2.2 |

**两个"明确"，Brief 里必须写死**：
- 🔴 **本轮产物性质**：开头标 `性质：概念探索（exploration only）` 或 `性质：正式素材制作（production asset）`。两者 prompt 规则不同（§2.3 vs §4.3），**不许混用**——概念图可含 UI，正式素材不许含整张 UI。
- 🔴 **事实来源优先级**：**真实业务数字、中文文案、交互逻辑一律以产品规范（spec.md / brand-spec.md）为准，GPT 输出不作数**。Brief 里每条数据后标注其真实来源。

**参考资产（可选、有条件时必用）**：
- **可用**：现有界面真机截图、已选定方向的渲染截图、品牌元素（logo / 色板 / 字体规范）。
- **怎么用**：走图生图 `--ref <截图>`（`/v1/images/edits`），把「保真结构 + 换视觉语言」写进 prompt——比纯文字描述稳得多。
- **红线**：参考图只提供**结构与气质**，其中的**数字/文案仍以 spec 为准**（截图里的旧数据不得进 prompt 当事实）。

> **Brief 是"探索"还是"素材"的判断门**：先判性质，再选 prompt 规则。**判断不出的，按概念探索处理**（更保守：探索态不污染交付）。

### 2.1 什么时候走这条

**App / Web / 交互原型**类任务，视觉方向尚未确定时——**默认优先**用 GPT 出三套差异化效果图。

**不适用的任务（强制回落 HTML/CSS，不调 GPT）**：不适合生图的任务不得为了「流程完整」强行生图——
- 幻灯片 / deck、信息图、数据可视化（结构由内容决定，靠 GPT 画文字必糊）
- 动画 / 宣传片（走 `storyboard-basics.md` 分镜卡）
- 纯排版 / 文档型产出
- 只需要微调既有界面的改动
- 用户明确说「不要效果图 / 直接写 HTML」

### 2.2 三方向的要求（与原有三方向门同构）

三套共用**同一份需求与核心功能**（即 Phase 3 spec，含「用户 + 核心行为」一行），差异必须在**视觉方向 / 布局 / 表达方式**上明显区分：

- ✅ **不只是换配色**：配色差异是入场券不是方向差异。三套应在**布局骨架、信息组织、视觉母题**上结构性不同
- ❌ **不虚构必要功能**：三套都要覆盖同一份核心功能，不得为了让某套好看而发明不存在的功能
- ✅ **以产品价值判断约束设计**：三套是同一件真实事的三个价值侧重（如 极简数字型 / 高密度仪表盘型 / 激励叙事型），不是三个臆想需求
- ✅ **标明概念参考**：效果图默认是「概念参考」，不是可直接交付的界面

**三套差异化逻辑**（沿用 Fallback 三套逻辑，只是产出换成效果图）：
- **逻辑一 · 秒数轮盘**：`date +%S` % N 从风格库取号，强制打破「每次都选安全极简」
- **逻辑二 · 现实参照**：锚定一个真实存在、设计极出色的标杆产品/站点，迁移其设计语言
- **逻辑三 · 最佳设计师**：设想预算无上限时最适合本产品的工作室/设计师，启用其设计哲学

**差异必须落到 prompt 上（不是只写在 Brief 里）**：三个方向的 prompt 至少三处结构性不同——**母题（visual motif）/ 布局骨架 / 视觉母题对应的形式元素**。若两个 prompt 的差别只在配色与形容词，**不算差异化**，退回重写。检验法：把三条 prompt 并排看，能否只读 prompt 就预言"这三张图会明显不同"？不能 → 差异不足。

> **参考资产参与差异化**：方向二（现实参照）优先用 `--ref` 喂真实标杆截图或本产品现有截图；方向三（最佳设计师）可喂品牌资产。方向一（轮盘）保持纯文字，作为「无既有惯性」的对照。

### 2.3 概念图 prompt 自动生成规则（英文）

概念图**允许出现 UI 元素**（它就是界面探索），但仍受反 slop 约束。**prompt 由 agent 从 spec 自动生成，不要求用户写**；提示词方法论复用 `huashu-gpt-image`（本 skill **不复制其功能**，只规定自动生成规则）。

🔴 **语言规则（硬）**：交给生图模型的 prompt **一律英文**——gpt-image 系列对英文指令最稳。中文只用于①与用户沟通 ②内部推理 ③需要「精确渲染的中文文案」时**以引号原样嵌入**（并注明 `render this Chinese text exactly`）。**验收口径**：任一新设计任务都能自动产出一段英文生图 prompt，无需用户参与。

**自动生成六槽位**（按序拼接；缺项由 spec 推导补全，不得留空）：

| # | 槽位 | 写什么 | 反例 |
|---|---|---|---|
| 1 | **Subject** | 谁的什么界面（具体产品 + 具体屏幕） | `an app` |
| 2 | **Core action** | 首屏第一眼服务的那件核心行为，**放最前** | 罗列全部功能 |
| 3 | **Layout & hierarchy** | 布局骨架 + 信息层级（谁大谁小） | `clean layout` |
| 4 | **Visual style** | **真实参照名**（工作室 / 设计师 / 产品），不用形容词 | `minimal elegant` |
| 5 | **Color & mood** | 底色 + 单 accent + 情绪基调（有色值更佳） | `nice colors` |
| 6 | **Medium & ratio** | 媒介与比例（iPhone home-screen mockup / upright 2:3 / no device frame） | 只写 `image` |

**必写禁令（每条 prompt 结尾固定带上）**：`no device frame unless showing the hardware`；非官方致敬加 `no brand watermark · unofficial tribute`；`no gradient slop · no emoji icons · no lorem text`。

**尺寸**：iPhone 端默认竖幅 `1024×1536`；桌面 Web 默认 `1536×1024` 或 `1920×1080`（deck 走原链路）。**比例诉求写进 prompt**，别假设传了 size 模型就照画（见下方 ⚠️）。

**落盘**：prompt 原文写入 `assets/img-prompts/<name>.md`（一图一档，见 §4.4）——为可复现与可迭代，不是为写文档。

**示例**（概念图 · 自动生成）：

> `iPhone home-screen mockup of a personal finance app, primary focus: one-tap expense logging, oversized amount input as the first-screen hero, single-column card stack with a bottom tab bar, visual style of the Stripe design team, warm off-white #FAF7F2 background with a single terracotta #C04A1A accent, upright 2:3 composition, no device frame, no brand watermark, no gradient slop, no emoji icons, no lorem text`

> ⚠️ **CPA 通路不保证按请求尺寸出图——「请求尺寸」与「实际返回尺寸」是两个值，不要混为一谈**（实测：请求 `1024×1536` → 返回 `1024×1536`（一致）；请求 `1024×1024` → 返回 `1254×1254`（不一致））。因此：**比例诉求写进 prompt**（如「竖幅 2:3 构图的手机界面」）以引导模型自选画布贴近目标比例；脚本只做最后一步像素适配——`--fit cover` 裁边满幅、`--fit contain` 补边不裁主体。**别假设「传了 size 模型就按此比例画」，也别据请求尺寸推断产物尺寸**，一律以实际落盘文件为准。

### 2.4 展示后必须停

三套效果图摆出来后**结束回合，等用户选择**——包括 autonomous / 无人值守会话。这是**真正只有用户能做的决策**，停轮不算阻塞。

## 3. 用户确认与方向锁定（Gate）

用户看完三套效果图后可以：

| 动作 | 处理 |
|---|---|
| 选择其中一版 | 该版成为设计方向基准 |
| 组合不同版本 | 明确记下「A 的布局 + B 的配色」这类组合原话 |
| 修改局部内容 | **允许对同一方向继续用 GPT 编辑图片**（图生图，见 §4.3） |
| 重新生成方案 | 重跑三方向探索 |

**🔴 在用户满意并确认前，不进入正式 UI 实现。**

**保留现有 Gate 文件机制**：用户选定后立刻把「展示了哪几版、效果图路径、用户选择原话」写入项目 `direction-approved.md`（协议见 SKILL.md「Gate文件协议」）。**「用户说继续」授权的是进入下一步，不是跳过这道门**；跳过必须用户明说，并记进 gate 文件。

**同一方向的后续微调不重复执行三方向探索**（命中 Fallback「唯一豁免」第 2 条：已选定方向后的迭代）。

## 3.5 概念图 → 视觉规范转译（🔴 本次核心：把"看中的图"变成"做得到的设计"）

> **这一步是全流程最容易断链的地方**：用户选了一张 GPT 概念图，然后 HTML/CSS 实现出来却是另一个东西——因为没人把"概念图里到底是哪个视觉决策打动了用户"翻译成可实现的规范。本节就是那道翻译。

**产物（每个选定方向一份）**：`visual-translation.md`（路径与 `direction-approved.md` 同级）。它把概念图拆成**三类**处置，逐条留痕，可追溯、可审计。

### 3.5.1 可提取（→ 进视觉规范）

从概念图里**只提取视觉语言**，不提取内容。逐项对照下表填 `visual-translation.md`：每条写 **【概念图里的表现】→【为什么值得吸收】→【HTML/CSS 怎么落实】**。

| 可提取维度 | 具体看什么 | HTML/CSS 落实方式 |
|---|---|---|
| **色彩关系** | 不是抄色值，而是**关系**：几个色？主/次/强调如何分工？对比强度？ | `:root` token 表；写清 each token 的**职责**（`--ink` 主文字 / `--accent` 唯一强调） |
| **材质与光影** | 扁平 or 有层次？阴影/描边/渐变的**克制程度**与**用在哪** | `box-shadow` / `border` / `linear-gradient`；注明「只用在 X 组件」 |
| **图标与奖章语言** | 图形是线性/面性/双描边？圆角半径感？图形隐喻 | 原生 SVG（**不照抄像素**，重画为统一图标语言）；见 §4.1 |
| **插画风格** | 手绘/几何/摄影感？线条/质感/留白 | 简单图形用 CSS/SVG；**复杂插画才走 §4 正式素材**（GPT 生成） |
| **情绪氛围** | 温度（冷静/温柔/庄重）、节奏（疏/密）、留白率 | 由字重、间距、圆角、留白共同决定；写成一句可检验的"气质条款" |
| **可实现的视觉表现** | 哪些一眼能做、成本低、维护友好 | 直接列 CSS 规则或组件改法 |

### 3.5.2 不得照搬（🔴 硬否决，逐条记入"否决清单"）

| 不得照搬 | 为什么 | 正确做法 |
|---|---|---|
| **虚构数据** | GPT 图里的次要数字/日期**几乎全是编的**（计步器实测：436 主数字对，但距离 0.34→0.32、消耗 17→18、时长 00:04→6分、日期全错） | 一律以 spec 真实数据为准；**把幻觉数据当事实 = 伪造数据，违反产品规范** |
| **错误中文** | 字形/用词/标点常错、可能多字缺字 | 文案以 spec 原文为准；GPT 图里的中文只作**版式参考**，不作文案来源 |
| **假交互** | 按钮是画上去的，不可点、无状态 | 交互以产品规范定义的状态机为准；原型必须真可交互 |
| **不符合产品规范的布局** | GPT 会"顺手"增删 tab、改信息层级、发明不存在的模块 | 结构边界（tab 数/页面数/必含模块）**以 spec 为准**，GPT 只是配色与气质参考 |
| **不可实现 / 高维护成本的效果** | 复杂光影、粒子、依赖位图的精细质感，用 CSS 硬做=脆且丑 | 能原生做的才做；做不到的**如实降级并标注**，或转正式素材 |

### 3.5.3 概念图 vs 正式素材 的边界（防止"把探索态当成品"）

| | 概念参考图（§2） | 正式设计素材（§4） |
|---|---|---|
| **用途** | 探索方向、给用户选 | 直接进产品，被工程引用 |
| **含 UI 吗** | 可以（它就是界面探索） | **不可以**（禁整张 UI、假按钮） |
| **可否交付** | ❌ 永不作为界面交付 | ✅ 可作为素材交付 |
| **数据** | 全部不可信 | 由设计提供规范，素材本身不含业务数据 |
| **落盘** | `design-demos/`（可丢弃） | `assets/images/`（需留存，附 `img-prompts/`） |

### 3.5.4 断链自检（进实现前必查）

- [ ] `visual-translation.md` 存在，且"可提取 / 否决 / 落实"三类**都有内容**（全空的说明没真看，回去看）
- [ ] 每条"落实"都指向**具体** CSS 规则 / 组件 / token，不是"提高质感"这类空话
- [ ] 否决清单覆盖了：数据、中文、交互、结构边界、不可实现效果**五类**（该方向没涉及的写"不适用"）
- [ ] 选定方向的**母题**在实现里有对应物（呼应 Fallback「form 来自内容的哪里」）
- [ ] 与 `direction-approved.md` 的**用户选择原话**逐条对齐——用户选中的特征，实现里找得到

> **判据**：用户能指着实现截图说"这正是我选那张图时想要的东西"。做不到 → 转译没完成，别进 §5 实现。

## 4. 正式产品图片素材

**这是独立能力，与概念效果图分开管理。**

### 4.1 用途分流（谁是图，谁不是图）

| 设计需要的元素 | 用什么 | 理由 |
|---|---|---|
| **原创插画 / 背景 / 场景图 / 氛围图** | ✅ **可用 GPT 生成** | 这类没有「真图」可言，GPT 生成即最优载体 |
| **真实产品图片 / 品牌 Logo** | ❌ 优先官方或用户提供的**真实素材**（§1.a 资产协议） | 生成的产品图/logo 一眼假，且失真品牌识别 |
| **图标 / 图表 / 按钮 / 文字** | ❌ 优先真实 UI 组件 / SVG / CSS | GPT 画 UI 文字必糊、按钮不可交互 |

### 4.2 概念图 ≠ 正式界面（红线）

**不能把整张 GPT App 效果图直接当成正式 App 界面交付。** 效果图是视觉意图的表达，不是可运行的界面——它没有真实布局、按钮不可点、内容不可动态更新。

### 4.3 正式素材 prompt 要点

- **语言与原规则同**：同 §2.3——prompt **用英文自动生成**，中文文案以引号原样嵌入并注明 `render this Chinese text exactly`
- **禁止包含整张 UI、虚假按钮、界面文字**（除必要的品牌名/必要标签，且需核实准确）
- **单一元素 / 可独立集成**：一张图一个用途（一个背景 / 一张插画），不要塞多个元素
- **留出集成余量**：居中或留白构图，便于裁切与叠加
- **需要透明背景或精确元素时**：走图生图（`--ref` 参考图编辑）或在 HTML 中做叠加，别指望一次成图

### 4.4 素材落地：目录与 metadata（复用现有机制，不建资产管理系统）

沿用项目目录约定，只加一处专用子目录：

```
项目名/
├── spec.md                    # 需求与真实数据（原有，事实来源）
├── design-brief.md            # Visual Brief（§2.0，三方向共同输入）
├── design-demos/              # 概念效果图（探索态，可丢弃）
│   ├── direction-a-<逻辑名>.png
│   ├── direction-b-<逻辑名>.png
│   └── direction-c-<逻辑名>.png
├── assets/
│   ├── images/                # 正式素材（集成进交付物，需留存）
│   │   ├── bg-<用途>.png
│   │   └── illustration-<用途>.png
│   └── img-prompts/           # 生成素材的 prompt 与来源（一图一档）
│       └── bg-<用途>.md
├── brand-spec.md              # 涉及品牌时（原有）
├── direction-approved.md      # 方向 Gate（原有，记录选中的效果图路径 + GPT 出图授权）
├── visual-translation.md      # 概念图→视觉规范转译（§3.5，GPT-first 通路必备）
└── handoff/                   # 设计交付包（§5 末 / design-handoff.md，交 Web/Android/PPT 时必备）
    ├── README.md · structure.md · design-tokens.md · states-interactions.md
    ├── copy-data.md · assets.md · adaptation-a11y.md
    └── baselines/*.png
```

**`assets/img-prompts/<名>.md` 至少记录**：生成用的**提示词原文**、**实际使用的图片文件名**、**原始图（若做过裁切/后处理）**、**素材用途**、**来源与模型**。**保存提示词是为了可复现与可迭代，不是为了写文档。**

> **原始图 vs 实际使用图**：脚本若做了像素适配/裁切，两版都留（原图存档，使用版进 `assets/images/`），避免「想改一点却发现只有裁切版」。

### 4.5 优先真实素材

- 真实产品图、品牌 Logo、官方 UI 截图 → **先走 §1.a 资产协议取真图**，取不到才用 GPT 生成并**明确标注是生成物**
- 真实素材与生成素材**分开存放**，在 `brand-spec.md` / `img-prompts/` 里注明来源，避免交付时混用

### 4.6 正式素材交付规格（🔴 进入产品前必须逐项落实）

概念图随便看看即可；**正式素材要被工程直接引用**，所以每张都过这张清单（写进 `img-prompts/<名>.md` 或素材清单）：

| 项 | 要求 |
|---|---|
| **用途与目标尺寸** | 用在哪（哪页/哪组件/哪种状态），目标像素与显示区域尺寸；**尺寸诉求写进 prompt**，落盘后**实测**并以实测值记录 |
| **文件格式** | PNG / WebP / JPG；**是否需要透明背景**；若需透明 → 图生图或 `chroma_key.py` 处理，不指望一次成图 |
| **Prompt / 模型 / 来源** | 提示词原文、实际模型名（来自 §1 检测，非硬编码）、生成时间、原始图（若裁过） |
| **验证项** | 尺寸、清晰度（非糊/非伪影）、裁切效果（主体不被切）、无 letterbox 黑边、色彩数非纯色 |
| **引用关系** | 素材对应哪个页面/组件；工程侧引用路径（如 `assets/images/bg-<用途>.png` → 组件 `HomeBanner`） |
| **可引用性** | 落进产品可访问的目录；Android 侧给 `res/drawable-*` 规格建议，Web 侧给相对路径——**工程拿来就能用** |

> **不是每种视觉元素都需要 GPT 生图**：简单图标 / 文字 / 布局 / 几何图形**优先原生 UI / SVG / CSS**（§4.1）。只在生图有明显价值时（原创插画、氛围背景、复杂质感）才用 GPT。**为"流程完整"而生的图 = 无价值生成步骤**，不做。

> **明确区分两类产物**（呼应 §3.5.3）：概念参考图落 `design-demos/`（探索态，可丢）；正式素材落 `assets/images/` + `img-prompts/`（集成态，留存并进交付包）。**交付包里出现的是后者，不是前者。**

## 4.7 开发阶段按需生成（Dev-time On-demand · 🔴 本节重点）

> **场景**：设计已交付（`handoff/` 已给实现端），**开发过程中**发现缺一个视觉素材——比如某个空状态要一张插画、某页要一张氛围背景、某组件要一个原创图形。这时由**实现端/开发 agent**发起素材需求，DesignWise 规范提供判断与生成规则。
>
> **与 §4 的区别**：§4 是**设计阶段**按已定方向预生成正式素材；本节是**开发阶段**的**按需补料**。两者共用同一套 prompt 规则（§4.3）与规格（§4.6），但**授权是分开的**（见下 §4.7.3）。

### 4.7.1 十步规程（缺素材时按序走）

| # | 步骤 | 动作 / 判据 |
|---|---|---|
| 1 | **识别需求** | 说清：哪一页/哪一组件、哪种状态、**为什么现有手段不够**（不是"想要图"）。产出一行素材需求：「用途 + 目标尺寸 + 为何必须位图」 |
| 2 | **先查复用** | 按顺序找：① 已交付的 `assets/images/`；② 项目已有的图/图标；③ `handoff/assets.md` 里已列的素材。**找到合格的就停，不生成**（🔴 不重复生成已有合格素材） |
| 3 | **判能否原生** | 简单图标 / 几何 / 图形 / 文字 / 布局 → **SVG / CSS / 原生组件**（§4.1）。只在"原创插画 / 氛围背景 / 复杂质感"这类**位图才有价值**时才继续往下 |
| 4 | **读设计上下文** | 读 `design-brief.md`（Visual Brief）+ `handoff/design-tokens.md`（Token）+ `visual-translation.md`（已选方向 + 视觉语言）+ `handoff/assets.md`。**素材必须继承已选定的视觉风格**——这一条保证"不因进入开发阶段而丢失已选方向" |
| 5 | **自动生成 prompt** | 用 §4.3 规则（英文、六槽位、必写禁令）自动产出。**不要求用户写 prompt**；风格槽位填 §4 读到的 token 色值 / 参照名，不用形容词 |
| 6 | **定模型** | 用 §1 默认模型（当前实测 `gpt-image-2.5`）。**不硬编码到其它文档**，走 §1 口径 |
| 7 | **查授权范围** | 核对本次生图的**范围**是否落在已有授权内（§4.7.3）。**不在范围内 → 停下申请，不得先斩后奏** |
| 8 | **调用生成** | 过 Gate 后调 `huashu-gpt-image`（`gen_via_cpa.py`，**不复制其实现**）。⚠️ **未授权时走 §4.7.4 非付费路线，不得静默扣费** |
| 9 | **验收新图** | 过 §4.6 六项（尺寸 / 格式与透明 / prompt与来源 / 清晰度与裁切 / 引用关系 / 可引用性）+ **风格一致性**：色值是否落在 `design-tokens.md` 的 token、气质是否与 `visual-translation.md` 一致。不合格 → 定向重生成一次（**不为微小差异反复生图**） |
| 10 | **登记入清单** | 写入 `handoff/assets.md` + `assets/img-prompts/<名>.md`（一图一档），登记用途/尺寸/来源/模型/引用关系。**实现端按清单引用**，不各自散落 |

### 4.7.2 素材需求记录格式（一图一档，追加进 `assets/img-prompts/`）

```
素材：bg-empty-state（开发阶段补 · 2026-10-14）
需求来源：<哪页/组件/状态>，为何必须位图：<一句话>
用途 / 目标尺寸：<页面区块> / 1024×768
Prompt：<自动生成的英文原文>
模型：gpt-image-2.5（§1 默认）
风格继承：token <--bg #F4F5F3> / <--navy #17375E>；参照 <visual-translation.md 的母题>
实际文件：`assets/images/<名>.png`（落盘后填实测尺寸与格式）
引用：<组件名> → res/drawable/bg_empty_state.png
授权依据：direction-approved.md「## GPT 出图授权」dev-asset 范围 · 第 N 张
```

### 4.7.3 🔴 授权分离（概念 ≠ 开发素材）

**概念图授权不会自动扩展为开发素材授权。** 两者是**两个独立的范围（scope）**，写在同一节里但分行记：

| 范围（scope） | 覆盖 | 典型额度 | 能否覆盖开发期补料 |
|---|---|---|---|
| `concept` | 三方向概念效果图 | 每方向 1 张 × 3 | ❌ **不能** |
| `dev-asset` | 开发阶段按需正式素材 | **用户明示的数量 + 用途** | ✅ 是 |

**记录格式**（`direction-approved.md` 的 `## GPT 出图授权` 一节内分行）：

```
| 范围 | 用户原话 | 模型 | 张数上限 | 用途 | 计费 |
| concept | 「授权：出 3 张概念图」 | gpt-image-2.5 | 3 | 三方向概念参考 | 是 |
| dev-asset | 「可以给空状态出一张背景图」 | gpt-image-2.5 | 1 | 今日页空状态背景 | 是 |
```

**硬规则**：
- **超出已授权范围**（数量用完 / 用途变了）→ **停下重新申请**，不得顺带多生成
- **只有 `concept` 范围**时发起开发素材 = **未授权** → 走 §4.7.4
- 未授权的判断口径同 §1.5：**用户本轮原话**才算数，沉默/推断/「上次同意过」无效

### 4.7.4 未授权时的非付费路线（不得静默扣费）

未获 `dev-asset` 授权，**不得调用生图**。按优先级提供替代：

1. **复用**（回到 §4.7.1 第 2 步）——再找一次项目里有没有能用的现成图
2. **原生**（回到第 3 步）——用 SVG / CSS / 渐变 / 几何拼出等效视觉，标注"非生图实现"
3. **诚实 placeholder**——留一个带尺寸标注的占位块 + 一句"此素材待制作"，**继续推进开发**，交付说明里点名
4. **申请授权**——把 §4.7.1 的素材需求 + 预计张数/费用整理成一句，请用户拍板

> **红线**：任何情况下**不得静默扣费**（无授权直接调用生图端点）。这与 §1.5 同源——本项目未授权就是不许发。

### 4.7.5 边界（谁做什么）

| 谁 | 负责 |
|---|---|
| **实现端 / 开发 agent** | 发起需求、走十步规程、按 `assets.md` 引用成品 |
| **DesignWise（本 skill）** | 提供判断规范（§4.7.1）、prompt 规则（§4.3）、规格（§4.6）、授权口径（§1.5/§4.7.3）、登记格式（§4.7.2） |
| **用户** | 授权 `dev-asset` 范围（数量 + 用途） |

> **不要求所有项目都生成图片**：多数开发期缺料可用复用或原生解决（第 2、3 步）。**只有位图确有价值时才走生图**——为"流程完整"生成 = 无价值步骤。

## 5. 正式实现（DesignWise 的活）

方向确认后，由 DesignWise 依据**已批准的效果图 + 设计 Spec + 产品功能需求 + 正式图片素材**实现真实 UI：

- **页面布局真实**（用 CSS Grid/Flex 真排版，不是把效果图当背景）
- **按钮和交互有效**（可点击、状态可切换）
- **内容可动态更新**（不是写死的图片）
- **适配目标屏幕**（真机尺寸 / 响应式）
- ❌ **不把视觉效果图作为静态界面交付**（§4.2 红线）

实现细节走原有链路：`references/app-prototype.md`（App/iOS）、`references/react-setup.md`（技术红线）、`references/product-value.md`（产品价值）。

**实现完成 ≠ 交付完成**：原型要交给 Web/Android 工程或 PPT 制作方落地，必须附**设计交付包**（页面结构 / 设计规范 / 状态与交互 / 真实文案与数据 / 素材清单 / 适配与无障碍 / 验收基准图）——**不许让开发 agent 对着截图猜**。完整契约见 `references/design-handoff.md`。

> 🔴 **HTML 原型 ≠ Android 最终实现代码**：HTML 是**设计交付物与视觉基准**，不是拿去编译的源码。Android 侧请按交付包用原生实现（Kotlin/Compose/XML），Web 侧按交付包选定技术栈实现。把原型 HTML 硬塞进 App 是反模式。

## 6. 验证与反馈闭环

**保留现有全部验收机制**：产品价值判断、Spec 一致性、Scope 冻结、UX 评审（`critique-guide.md` 5 维度 + 用户价值 + Spec 核验）、浏览器验证（`references/verification.md`）。

### 6.1 视觉还原检查（轻量，对比概念图 vs 实现）

对比 **GPT 已确认效果图** 与 **DesignWise 真实渲染截图**，识别明显偏差：

| 检查项 | 关注什么 |
|---|---|
| **布局偏差** | 主要区块的位置/比例关系是否走样（首屏核心行为是否仍在视觉首要位置） |
| **字体层级差异** | 标题/正文/标签的大小对比是否被压平 |
| **图片素材错误** | 素材是否错位、拉伸、还是用错了图 |
| **配色与视觉气质偏差** | 主色/底色/情绪基调是否跑偏 |

**判定原则**：**不要求机械像素级一致**——以**用户确认的设计意图**和**真实产品可用性**为准。效果图是意图，实现对意图负责，不对像素负责。

**情感意图核对（轻量，可跳过）**：若 Brief 第 4 段定义过情绪机会，对照实现看一眼——**那处机会在实现里是保留了，还是被削弱了？** 判定唯一标准仍是「用户会不会真的这样感受」（`references/product-value.md` §0.5），**不是**「效果图里有所以实现必须照做」：概念图里的情绪表达**本来就是探索态**，实现可以选择不做。

**同时验证**核心功能与交互（点击测试，`pageerror` 为 0）。

### 6.2 闭环检查清单（✅/❌ + 证据，逐项写进交付报告）

| # | 检查 | 判据 | 证据 |
|---|---|---|---|
| 1 | **原始需求是否保留** | 逐条比对 spec 的功能/边界，无增删 | spec.md ↔ 实现页面 diff |
| 2 | **用户选择的视觉方向是否正确继承** | `visual-translation.md` 的"落实"逐条在实现里找得到；母题有对应物 | 截图标注 + 转译表 |
| 3 | **GPT 虚构数据是否被排除** | 实现里所有数字/日期 = spec 真实值，**零幻觉值** | 数值逐项核对表（计步器实测过 4 项幻觉） |
| 4 | **正式素材是否可被工程引用** | §4.6 清单每张素材都过；路径可解析 | 素材清单 + 引用路径 |
| 5 | **HTML 页面是否正常渲染** | 无 console error、`pageerror`=0、无溢出/截断 | `scripts/verify.py` 输出 |
| 6 | **交付内容是否完整** | `design-handoff.md` 六段齐全（§10） | 交付包清单 |
| 7 | **截图 vs 设计基准差异** | §6.1 偏差清单，只修实质偏差 | 偏差清单 |
| 8 | **情感价值点是否可信（可选）** | Brief 第 4 段若有情绪机会 → 说得出「谁 / 哪个时刻 / 因为什么」；说不出即装饰，删掉不算缺陷 | 一句话说明，或标 N/A |

### 6.3 定向修复，不推倒重来

**发现问题 → 只修被点名的实质项**，复验范围按缺陷影响面决定，**不重跑全流程、不重新生成全部设计**。风格/措辞/可读性偏好不算实质问题，不改。

**输出**：偏差清单（现状 / 是否影响意图 / 改什么），只修实质偏差，不为「更像效果图」牺牲可用性。

## 7. 费用与重复调用治理

- **概念阶段**：每个方向默认只出 1 张；三方向一次跑完，不逐张试探
- **禁止无条件重试**：一次调用只试一次，失败先读原因再决定（分档判定见 `gen_via_cpa.py` 头部）
- **编辑优先**：已在某方向上的微调走图生图（`--ref`），不从零重新生成
- **正式素材**：方向锁定后才生成，且**复用**已有素材，不为验证反复生成
- **同方向微调不重复三方向探索**（§3）
- **付费调用前置 = 付费资源授权 Gate**（§1.5）：涉及按量计费的通道，先核实计费方式与预计费用；**未获明确费用授权时先报告并请求确认，不得擅自产生付费请求**（物化落档与四要素见 §1.5，另见 SKILL.md 与 `SECURITY.md`）

## 8. 降级与能力映射（agent-agnostic）

本文件按**能力**而非工具名编写（呼应 `references/runtime-adapters.md`）：

| 能力 | 本机已验证载体 | 缺失时 |
|---|---|---|
| **GPT 图像生成** | `huashu-gpt-image` 技能自带的 `gen_via_cpa.py`（走本机 CPA，OpenAI 兼容 `/v1/images/*`） | OpenAI Images API（自备 key）；再不行 → **回落原有 HTML/CSS 三方向探索** |
| **图生图 / 参考图编辑** | 同上脚本 `--ref`（`/v1/images/edits`） | 无编辑能力时：改 prompt 重新生成，或转 HTML/CSS 微调 |
| **浏览器截图** | 内置 browser 工具 / `scripts/verify.py` | 无截图时让用户自己打开看，并在交付说明标注「视觉还原检查未自动执行」 |

**降级底线**：GPT 不可用 → **保留原有 HTML/CSS 设计能力不变**（60 种风格库、三方向硬门、资产协议、反 slop 底线一条不少）。**降级牺牲的是「探索通路」，绝不牺牲反 slop 底线与真实资产协议。**

## 9. 反模式（做了就背离本文目的）

| 反模式 | 为什么错 |
|---|---|
| **把效果图当界面交付** | 假界面：按钮不可点、内容不可更新，是伪装成成品的概念图 |
| **把 GPT 当默认答案** | 幻灯片/信息图/动画等结构性任务强上 GPT = 文字糊、结构错，原有 HTML/CSS 更强 |
| **三方向只是换配色** | 用户拿不到真实的方向选择依据，等于只给了 1 个方向 |
| **发现配置就报告「生图可用」** | 未经真实出图验证 = 假装成功（§1 铁律） |
| **用 HTML 截图冒充 GPT 生成图** | 欺骗性交付，且掩盖通路不可用的真实阻塞 |
| **无授权就发起付费调用** | 越过费用授权边界（§7） |
| **为验证无限生成图片** | 费用失控；应复用已有测试素材 |
| **真实产品图/Logo 用 GPT 生成** | 一眼假 + 失真品牌识别；应走 §1.a 取真图 |
| **概念图与正式素材混放** | 交付时易误用；且无法区分「探索态」与「集成态」 |
| **把 GPT 图里的数据/中文当事实** | 模型幻觉：次要数字、日期、中文常编错；一律以 spec 为准（§3.5.2） |
| **用户选定方向后直接开写 HTML，不转译** | 断链：实现与用户所选概念图对不上（§3.5 存在的原因） |
| **把原型 HTML 当 Android 最终代码** | 原型是设计基准不是产品源码；Android/Web 按交付包各自实现（`design-handoff.md`） |
| **让开发 agent 对着截图猜规格** | 交付包缺原理化规格 = 返工；必须给 token / 状态 / 数据口径（`design-handoff.md`） |
| **型号版本号抄进多个文档** | 升级时多处失同步；只在本文件 §1 写口径，别处引用 |
